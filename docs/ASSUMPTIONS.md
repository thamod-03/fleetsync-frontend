## Customer payment/invoice/Chat follow-up — revised authorization

The latest user request explicitly authorizes fictional card details for successful/unsuccessful payment, PDF invoice download, and the Customer Chat interactions in the supplied frames. This supersedes the earlier provisional deferrals of card entry, non-tax PDF generation and direct Customer–assigned-staff pairs. No real gateway, legal tax rules, refunds, automatic trip prerequisites, production authentication or backend is introduced.

Re-inspected read-only Figma context/screenshots for `160:5892`, `161:5978`, `161:6347`, `161:6668` and `164:7038`. Only exact provided non-bank fixture details validate; all card fields remain in React memory and are discarded after navigation. The service accepts only a known instrument ID, derives amount/customer/order from the accepted quotation and never receives or stores full card details. Optional instrumentId/cardLast4 metadata is backward compatible. Legacy callers still work without a supplied instrument. Pending attempts retain their original instrument; failed attempts may be retried with a new request and another card. Clicking Pay is the explicit confirmation; the additional off-design confirmation checkbox was removed, while the service still requires confirmed=true.

The application now downloads an actual PDF through downloadCustomerInvoice. It requires a successful owned payment, rechecks access after asynchronous generation, and creates no new payment or notification on download. Fonts are embedded from existing local Inter assets; document strings are drawn as text, not interpreted as HTML. A basic Payment Invoice is authorized, but tax/issuer/legal invoice requirements remain undefined: no VAT, legal invoice numbering, registration number or tax claim is fabricated. PDF uses the actual payment reference, dates where recorded, quotation charges and customer/company/order records, with explicit local-simulation/non-tax wording. It does not claim external funds or receipt email delivery. A generated sample was rendered with temporary PDFium tooling and visually checked. jsPDF is the only added application dependency.

Conversations remain private two-person threads. The existing Coordinator/participant representation is retained unchanged for legacy records. A backward-compatible CustomerStaff variant adds customerUserId and participantId for the order's owning Customer and actually assigned Driver/Mechanic. Conversation-owner helpers centralize pair identity; schema validation checks roles, order ownership, sender/recipient and message references. Dynamic availability still follows the existing latest-active-trip, otherwise latest-recorded-trip projection. No company-wide Customer access, reassignment operation, resource release or historical-access policy is invented. Obsolete/unrelated pairs cannot be opened or sent to through the current service projection, while saved history remains stored. Customer–staff threads are not Coordinator group chats; Coordinator private threads remain unchanged. Notifications go to the actual other member once per committed message. Role switching, refresh, local unread state and Reset reuse the same canonical store.

No snapshot reset is required: legacy Coordinator pairs and payments remain valid; new fields/variants are added through existing schemas. No second dataset, store or real-time transport is introduced. Fixtures are excluded from Production by existing compile-time adapter gates. Attachments, remote receipts and Driver/Mechanic application interfaces remain outside this follow-up. Formal tax invoices, expiry/revision/refund policy, production gateway/session security and reassignment-history rules remain team/backend work.

The install audit reports seven existing high-severity entries in the unchanged shadcn/ts-morph/glob dependency chain. These versions were compared against the original lockfile; no new jsPDF advisory was reported. Unrelated major-version or force fixes were deliberately not applied. Browser-based card interaction, native PDF download, staff-thread switching and responsive/Figma comparison still require manual checks when a browser is connected.

### Existing permissions and relationships remain authoritative

The existing model is a set of private direct pairs between a Coordinator and the owning Customer, assigned Driver or assigned Mechanic. It is not a group thread. All active Coordinators currently have order access because assigned-Coordinator/depot grants are undefined. Customer access remains person-owned, never automatically company-wide. A Customer can select their Coordinator pair and see assigned resource context, but cannot read/send to Coordinator–staff pairs or directly message staff. Staff cards are explicitly unavailable until direct Customer–staff permissions and a compatible conversation contract are approved. The populated design alone does not authorize broadening that rule.

The existing assignment projection prefers the latest active trip, otherwise the latest recorded trip. Customer context uses that same trip, without changing release, cancellation/completion or reassignment policies. Historical access after reassignment, order closure, retention and membership revocation remain unresolved. Existing projections omit obsolete unrelated pairs; no new archival or permanent revocation rule is introduced. Orders without a recorded trip show no guessed Driver/Mechanic. Customer's own identity remains the authenticated session/contact, not a participant ID supplied by the browser.

Existing shared services perform membership checks after latency for reads/sends/local unread updates. Sender, recipient and order IDs derive from the authenticated pair, stripping attempted submitted identity overrides. This batch also rejects chat send/read operations if the session changes during simulated latency, including when both old/new personas belong to the same pair. The UI selects only returned authorized rooms; explicit unknown order or conversation parameters show an unavailable state and never fall back to another thread. Queries do not create conversations or notifications. A first send atomically stores the pair/message/recipient notice; same-ID same-content retries return that record without duplicate notices. Message sorting, readBy flags, notification boundary and persistence are shared with Coordinator Chat. Opening a thread updates only local unread state, not a claim that a remote user has read it.

Customer layout uses the same pane with a Customer order link and scoped visual styling. Presentation does not import stores/mock factories or read localStorage. Optional OrderRoom.assignmentContext contains joined staff identities, vehicle registration and actual start time only when recorded; it is a query projection, not a new stored domain or second dataset. Existing ApplicationServices signatures, conversation/message schemas, store, snapshot version/defaults, notification model and reset mechanism are unchanged. Existing snapshots need no migration or reset.

Customer navigation is connected across Dashboard, Orders, Quotations, Payments/history and Chat. Order/quotation Open chat actions retain their original order ID; View order returns to its owned detail route. The main twelve Customer Figma screen states now have interfaces. Shared Profile & settings (`119:3585`) remains unimplemented: its profile photo, personal-detail change approval, password/security and change-request history require approved contracts, and the frame's sample Fleet Owner data must not be invented for Customers. Profile remains visibly unavailable. Formal invoice generation/download, direct staff messaging, attachments and real financial/delivery integration remain unavailable. No new refund, quotation revision, tax invoice, profile approval, company grant or mobile workflow is implemented.

Focused tests cover owner/same-company isolation, unauthorized pair IDs, sender spoofing, both role directions, order associations, empty/oversized input, duplicate/concurrent/reload retries, local notification counts, chronological history, local unread flags, persona-switch races, saved assignment context and reset. Downloaded Figma SVGs supply the new content icons; existing shared sidebar/header/branding remain unchanged. No Figma writes occurred.

Figma's automatic expiry/repricing and payment-before-trip scheduling copy is not asserted: expiry, revisions, withdrawal and quote/payment prerequisites remain unresolved. The recorded validUntil is displayed but no automatic expiry or decision cutoff is invented. Existing publication still requires a future validity value; issued quotes remain immutable through current Coordinator contracts. Accepting leads to payment; declining records a decision. The order becomes Accepted/Declined using existing statuses, with no new Paid order status and no change to trip eligibility, reservations or lifecycle.

Real card entry and claims about a secure gateway, bank declines, money received or receipt emails are replaced at the action boundary with truthful local outcomes. Name/card/expiry/CVV structure remains visually present as read-only placeholders without form names, sensitive values or credential persistence. The form validates the supported Card method and explicit amount confirmation using RHF/Zod; payable amount is never accepted from a form. The local provider reports Succeeded/Failed in existing domain terminology; those are stored simulation results, not bank authorizations. No remote delivery or payment security is claimed. No generic demo banners were added.

### Shared decisions, authorization and payment consistency

Billing services derive the active Customer person from the saved session, preserving Batch 01's person-scoped policy even within a shared company. All quotation, transaction and invoice queries/mutations check ownership through canonical order/customer relationships; Draft quotations and their payment records remain hidden. Coordinator decisions are visible through existing order/report projections. Queries never emit notifications. Acceptance/decline commit decision metadata, order status, audit event and one local notice per active Coordinator together. Exact decision-request retries are idempotent; other decisions after Pending are rejected. Published quotation revisions remain unsupported rather than guessed.

PaymentInput includes only quotation ID, request UUID, Card method and confirmation. The service obtains amount/currency/customer/order from the accepted quote, persists Pending before processing, then commits the final result, audit and local Customer/Coordinator notices. One in-flight operation per pending payment is shared across service instances over the same store. An existing success for the order returns the existing record; no second payment is generated. Exact failed retries return that failure; a new request after failure creates a new attempt. Network/provider failure leaves a resumable Pending record, not a fabricated failure or success. Refresh performs queries only; resumption requires an explicit action. Reset/change checks prevent a delayed result from recreating removed records. Notification-preparation failure leaves Pending for safe local retry and does not claim success. A real provider must supply durable server-side idempotency/transactions before integration; cross-tab/machine concurrency is not guaranteed by localStorage.

Only Pending, Succeeded and Failed are used. Leaving the payment page does not fabricate Cancelled/abandoned records, release financial obligations, or change trip state; abandonment/cancellation, installments, refunds, credits, multiple issued quotes and financial allocation remain unapproved. Successful payment does not create or start a trip.

### Compatibility, reports, invoice boundary and environment protection

Optional fields preserve version-1 snapshots: quotation publishedAt/decidedAt/decidedBy/decisionRequestId and payment orderId/customerId/requestId/createdAt/completedAt/method/reference/failureReason. Old IDs and amounts remain intact; missing dates, card digits, methods and issuer information are not inferred. New payment ownership/amount relationships and successful-payment uniqueness are checked on persisted data; preexisting legacy records remain readable. Reset restores canonical seed data, including the original undated payment. No new store or storage namespace exists, and presentation never reads localStorage.

Payment History defaults to All time so undated historical records remain visible. Bounded periods exclude undated records; monthly/yearly totals use recorded completion/creation times and explicitly exclude undated history. Summary cards cover all owned records, while table filters narrow the list. Coordinator revenue retains its existing order-cohort basis, including shared successful payments; adding payment dates does not silently redefine report accounting.

There is no approved Invoice model, invoice-number/issuer contract, tax policy or actual document. Invoice availability is behind the typed adapter method, requires an owned Succeeded payment, and returns the real related payment/order/quote/company with available=false. The embedded preview uses those records and is labelled Payment record, never Tax invoice; PDF download is disabled with an explanatory response. Dedicated invoice generation/download remains blocked by missing requirements, not substituted with an invented legal document. No dependency is needed until that contract is supplied.

The payment mock provider is imported only through the existing local/explicit Preview adapter gate. Production uses unavailable services and contains no payment mocks. One-shot failure controls live only in the local development utility, excluded from built Preview and Production. They do not change deployment settings. Default Preview processing succeeds locally; injected providers/local utilities exercise failure and recovery. Reset also clears the transient next-failure flag. No actual gateway, bank credential, card data, external email, push, deployment or Figma modification is introduced.

## Customer Batch 01 — inspected frames, contracts and provisional behavior

Read-only design context and screenshots were inspected for Customer Dashboard (`150:5292`), New order / 1 Route (`152:5434`), / 2 Cargo (`155:5503`), / 3 Review (`156:5595`), My orders (`157:5675`), and Order details (`158:5805`). The Screens page (`33:437`) supplied exact frame IDs. Existing FleetSync sidebar/header, Inter/JetBrains Mono typography, colors, cards, status styles and loading/error primitives are reused. Wizard state is one URL; mobile stacking is a practical fallback because separate approved mobile frames were not supplied. Figma was not changed.

### Identity, submission and shared state

The existing EER specialization treats a Customer as a person linked to a company. No company-wide grant/administrator contract exists. Customer services therefore retain the existing getOrder ownership policy: only the signed-in person's customerId, with no automatic access to other contacts' orders even in the same company. Company identity is supplied by the linked profile, never accepted from submitted form fields. Pending/non-Customer sessions cannot create or read orders through these services. Account permissions are rechecked after mock latency, at commit time.

The initial transport-order status is Submitted, as required by existing Coordinator contracts. A single atomic save appends the order and its audit event; it does not create trips, resource reservations, payments or quotations. Queries use projectOrders and the canonical Zustand dataset, so new Customer submissions appear directly in Coordinator overview/list/review and future quotation workflows. No extra dataset/store is introduced. Duplicate suppression is keyed by customerId plus a request UUID with a normalized payload fingerprint. Exact retries return the same order; changed payloads with an already-used key are rejected. An intentional new order receives a new key. There is no cross-tab/server transaction guarantee or content-based ban on identical intentional orders.

### Form fields and safe compatibility

The approved frames require structured pickup/destination addresses and cities, pickup date/time, pickup contact and receiver details, delivery deadline, cargo type/packing/description/weight and handling. Existing origin/destination remain cities. Optional new order fields preserve addresses, contact names/phones, deliveryBy, packing, cargoDescription, palletCount and palletSize. Existing weightTonnes, pallets, handling and customerNote remain compatible projections for Coordinator screens. Internal submissionKey/submissionFingerprint are temporary idempotency metadata, not an approved database design. Old IDs/snapshots remain valid because all additions are optional. Saved submission keys are validated for uniqueness.

Dates are entered in browser-local time and stored as UTC ISO timestamps. The typed mock input currently carries local form date/time values; a future API adapter must send an explicit timezone/offset or normalize before server interpretation. A delivery deadline at or after pickup is valid; equality is allowed. No past-date cutoff, travel-time estimate, different-city restriction, capacity gate or quote/payment prerequisite is invented. Delivery deadline is never mapped to estimatedReturnAt, because delivery time and vehicle return are different concepts. Canonical saved-data validation rejects a recorded deadline earlier than pickup.

Weight must be finite/positive and is converted from kg to tonnes. Pallet count, if provided, is a whole nonnegative number; count/size remain optional because a non-pallet shipment policy is not supplied. Cargo type, packing and description are required; notes/handling are optional. Phone validation permits digits and standard separators without imposing a national-number/checksum rule. Field lengths are bounded for input safety. Exact catalogue choices, mandatory pallet rules and company-level authorization remain team decisions.

The city/cargo/packing selection catalogue was not provided beyond populated examples, so fields permit text entry. City suggestions derive from the customer's own orders, and Pallets is the inspected packing suggestion. The Saved locations control reuses previous owned pickup addresses; no separate saved-location CRUD/database is invented and the empty control is disabled. A future saved-location service should replace that provisional lookup. Wizard values survive step changes and review edits in memory; unfinished forms are not persisted as Draft orders. Refresh resets an unfinished wizard. Once submitted, the order and retry metadata persist through the existing snapshot mechanism and Reset Demo Data removes them.

### Presentation and deferred actions

Lists and dashboards derive status through one Customer projection: Submitted → Pending review, current Assigned/In Progress/Completed/Cancelled trip status where available, and Declined → Quote declined. These are presentation labels, not new order/trip statuses. Trip Assigned replaces Figma Scheduled terminology. Monthly completion counts use recorded return timestamps and the captured UTC month. Open-order totals exclude completed/cancelled/declined records. Pending quotations retain their recorded status; no new automatic expiry transition is introduced. Draft quotations and their payments never appear in Customer workspace/details.

My orders defaults to the inspected last-three-month period with All time available; status counts use all owned orders while the table applies period/search/tab filters. Order IDs use the existing identifier contract with UUID-generated new IDs, not fabricated reserved Figma numbers. Populated Figma names/addresses/order totals are not copied into components. Detail timelines use recorded trip timestamps and audit events, never fake Driver app updates, payment dates or quote-acceptance timestamps. Mechanic is displayed with the mandatory vehicle/driver assignment even though the populated Customer reference only shows vehicle/driver.

Quotation-response and payment screens are not implemented. Designed quotation/payment/invoice/Chat/Profile actions remain visibly disabled with an unavailable-feature title, preserving their positions without dead links. Existing paid records may appear as read-only summaries, but no payment method/card digits/date or invoice is invented. Next-step marketing copy follows Figma; submission confirmation only states the order is saved for Coordinator review and never claims email delivery. Normal screens contain no university/mock-data notices. Coordinator review's existing layout now shows optional submitted addresses/contact/description so the cross-role handoff includes the entered information.

## Coordinator Batch 03 — reports and communications

### Read-only designs and presentation

Inspected design context, screenshots and metadata for Operational reports (`142:5026`), Chat (`145:5122`), and Mail / Inbox (`229:10801`). The Coordinator tracker (`122:4965`) exposes these entries but no separate compose, reply/forward, generated-category variants or export dialogs. Compose uses the existing Base UI dialog and FleetSync field/button styles. The PDF workflow uses the native browser print dialog. Existing shells/tokens are reused; mobile stacking is a practical fallback because separate approved mobile frames are absent. Figma was not modified.

CSV is the implemented spreadsheet format and is labelled Export CSV instead of falsely offering XLSX. PDF means browser Print → Save as PDF, not a binary PDF-generation dependency. Both exports use the displayed report snapshot, including summary values, rows, chart data, filters and calculation notes; print displays the chart's underlying daily figures as a table. Recent exports store prepared snapshots and can be reproduced after refresh; they do not claim the user saved a file or completed printing. Old fictional export history and unrelated populated Figma messages/documents are not copied into UI components.

### Provisional reporting semantics and missing data

Only four inspected categories are implemented: Trip summary, Vehicle utilisation, Driver activity, Orders and payments. Maintenance Cost scope is unresolved and the model has no cost/service-history records, so no maintenance cost, idle-day, service-day, on-time or efficiency percentage is invented. Vehicle utilisation shows actual assignment counts, completed trips, recorded distance and **scheduled** calendar days. It is not measured operating utilisation. Under All customers/base, zero-activity resources remain visible; filters can exclude unrelated resources.

Filters use inclusive UTC calendar dates. Completed trips use actual return time; Cancelled uses cancellation time when recorded; others use scheduled start, then trip creation, then related order creation. Legacy dates are not fabricated. Orders use creation date. Base uses the assigned vehicle's recorded homeBase; an order without an assignment cannot be attributed to a base. These cohort choices need confirmation against reporting requirements, especially trip overlap versus start/completion-period inclusion. Current filters select a trip's event/cohort date, not every day on which a long trip overlaps a period. Scheduled-day counts use known scheduled windows clipped to the selected period and deduplicate dates per vehicle.

Distance is final minus starting odometer for Completed trips only. Missing start readings yield Not recorded, not estimated distance from order routes. Revenue is the sum of recorded Succeeded payments for the selected order cohort; payment timestamps are absent, so it is not receipts during the selected period. Payments are counted once even with multiple trips for an order. Trip-summary grouped revenue shows Not attributable when an order references several vehicle types; no payment split is guessed. The overall total still counts each order payment once. Financial allocation requires an approved rule/backend contract. Issued quotation counts exclude Drafts. No period comparison, customer-cancellation attribution or payment timing is fabricated. Generated reports are snapshots and update when regenerated; history intentionally retains the exported snapshot.

### Conversation identity and access

Each direct conversation has a stable ID, order ID, Coordinator ID and peer ID. A peer is the order's owning customer or a driver/mechanic referenced by its current trip. All active Coordinators may access submitted orders because no depot/assigned-Coordinator ownership contract exists. Where several historical trips exist, the latest active assignment is preferred, otherwise the latest recorded assignment. Completion/cancellation does not independently revoke chat access or release resources; that policy remains unresolved. No reassignment mutation or mobile UI is added.

Room lists and messages are projected from shared records; queries are non-mutating. Available pair IDs are deterministic until first message save, which persists the conversation and message atomically. Existing saved pair IDs are reused. Customers and staff see only their own direct pair with a Coordinator, not other people's messages; unrelated staff/customers and Administrator accounts cannot access those pairs. The same typed service can support later Customer/mobile interfaces, although current web authentication still excludes Driver/Mechanic roles. Historical access after reassignment, order closure and retention needs team confirmation; new eligibility projections do not expose obsolete unrelated pair histories.

Message text is trimmed, required and limited to 4,000 characters. A caller-provided message ID makes exact retries idempotent; conflicting reuse is rejected. Only the signed-in recipient may mark that pair read. These are local-view flags, never remote delivered/seen receipts. The outgoing UI says Stored locally; no fake online presence, background polling, WebSocket or real-time delivery is added. Legacy messages missing order context remain stored but hidden from order rooms because inferring their order would be ambiguous.

### Internal mail and local notifications

The shared mail contract is reusable by Administrators and Coordinators and restricts recipients to active users of those roles. Sender comes from the session, never a submitted sender field. No self-mail is offered. These match the inspected internal-mail roles; cross-role/broadcast mailbox policy still needs confirmation. Compose may choose multiple explicit recipients; no automatic broadcast is invented. Sent records are visible to their sender and recipients, private Drafts only to the sender. Subject/body are required on send (200/20,000-character bounds); drafts may be incomplete. Stored messages are immutable. Exact request-ID retries do not duplicate mail or notifications. Reply/forward links must reference a message visible to the caller. Stars, local read flags and trash are per-user; trash is reversible and does not delete another user's copy.

No real mailbox, SMTP, push, email delivery, document upload or attachment bytes are connected. The seeded internal message uses existing fictional identities. The populated Figma attachments do not exist in this dataset and are not fabricated. Message state is Stored locally; action feedback explicitly says no external email was sent. The existing Notification model is reused via an injectable message-notification boundary. One recipient notice is prepared per committed message; notification-preparation failure prevents partial writes. Reads, queries and refresh never enqueue notices. Existing trip/quotation notification behavior is unchanged.

### Persistence, integration and verification

Version-1 snapshots default absent conversations/mail/export collections to empty arrays and absent chat read metadata to an empty array. Scoped messages validate order/pair/participant references; legacy unscoped records remain intact. Mail validates user roles, related-message references and per-user flags. Authentication build gates, Vercel files/settings, existing domain IDs, trip lifecycle and resource-release rules are unchanged. Reports/Chat/Mail routes retain the Coordinator role guard. Tests cover calculations, filtered export equivalence, empty/invalid data, role isolation, message validation, private drafts, read flags, retries, atomic notifications, persistence/migration/reset, rendered markup and existing regressions. Manual checks remain for 1440px Figma comparison, mobile/tablet scrolling, dialog focus/keyboard operation, chat auto-scroll, CSV download and browser print-to-PDF.
